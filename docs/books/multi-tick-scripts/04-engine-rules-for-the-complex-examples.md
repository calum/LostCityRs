# Part A. Engine rules the chapters rely on (re-verified)

Each chapter cites these as **E1..E12** so the long engine explanations are not repeated. Each rule below was re-read in source for this note; the doc rules it matches are named.

**E1. Order of one player's turn in phase 5 (`processPlayers`).** Undelay, then resume a `SUSPENDED` script, then `processQueues()` (normal then weak queue), then normal timers, then soft timers (both skipped if `loggingOut`), then the engine queue, then facing and `processInteraction`. Source: `Engine-TS/src/engine/World.ts:692` (undelay), `Engine-TS/src/engine/World.ts:695-696` (resume), `Engine-TS/src/engine/World.ts:701` (`processQueues`), `Engine-TS/src/engine/World.ts:704`/`Engine-TS/src/engine/World.ts:706` (timers), `Engine-TS/src/engine/World.ts:709` (engine queue). Matches 05#4-5, 05#18. `currentTick` is incremented once per cycle at `Engine-TS/src/engine/World.ts:503`.

**E2. `p_delay(n)` and `p_arrivedelay`.** Source: `Engine-TS/src/engine/script/handlers/PlayerOps.ts:376-380`
```ts
    [ScriptOpcode.P_DELAY]: state => {
        state.activePlayer.delayed = true;
        state.activePlayer.delayedUntil = World.currentTick + 1 + check(state.popInt(), NumberNotNull);
        state.execution = ScriptState.SUSPENDED;
```
- A script that calls `p_delay(n)` in tick T has `delayedUntil = T+1+n`, and (E1) is resumed in step 2 of the player's phase-5 turn in tick T+1+n. So `p_delay(0)` is "continue next tick", `p_delay(1)` is "continue in two ticks". (inference from E1 and this handler; same as the inference in 05§Inferences.)
- `p_arrivedelay` (`Engine-TS/src/engine/script/handlers/PlayerOps.ts:359-367`) returns doing nothing if `lastMovement < currentTick`, i.e. if the player did not move this tick; otherwise it behaves like `p_delay(0)` (`delayedUntil = currentTick + 1`, `SUSPENDED`).
- Content `engine.rs2` marks both as "Requires protected access" (`Content/scripts/engine.rs2:169-174`).

**E3. Where a suspended script is stored.** `Player.executeScript` (`Engine-TS/src/engine/entity/Player.ts:2202-2228`): for any state other than finished/aborted/`WORLD_SUSPENDED`/`NPC_SUSPENDED` (so `SUSPENDED`, `PAUSEBUTTON`, `COUNTDIALOG`) it does `script.activePlayer.activeScript = script; script.activePlayer.protect = protect;` (`Engine-TS/src/engine/entity/Player.ts:2216-2218`). There is one `activeScript` slot per player and the assignment has no check for an existing value. When a script finishes and it is the player's `activeScript`, the slot is cleared and, unless a `MAIN` modal is open, `closeModal(false)` runs (`Engine-TS/src/engine/entity/Player.ts:2219-2227`), which closes a chat dialogue but does not clear the weak queue. The script's `ScriptState` (program counter, locals, frames, active player/npc pointers) is the object that is stored, so locals survive the suspension: `ScriptState.pc`, `intLocals`, `frames` at `Engine-TS/src/engine/script/ScriptState.ts:16-17`, `Engine-TS/src/engine/script/ScriptState.ts:41-45`; `ScriptRunner.execute` continues from the saved `pc` (`Engine-TS/src/engine/script/ScriptRunner.ts:121-157`).

**E4. `busy()` / `canAccess()`.** `busy()` = `delayed || containsModalInterface()` where only `MAIN` and `CHAT` modals count; `canAccess()` = `!protect && !busy()`, always true during `World.shutdown`. Source: `Engine-TS/src/engine/entity/Player.ts:816-832`. Gate for the normal queue, weak queue, normal timers and engine queue (`Engine-TS/src/engine/entity/Player.ts:904`, `Engine-TS/src/engine/entity/Player.ts:919`, `Engine-TS/src/engine/entity/Player.ts:953`, `Engine-TS/src/engine/entity/Player.ts:663`); not for soft timers (`Engine-TS/src/engine/entity/Player.ts:953`). 05#8.

**E5. Packets while delayed are dropped, not deferred.** `MoveClickHandler` (`Engine-TS/src/network/game/client/handler/MoveClickHandler.ts:12-15`) and `OpNpcHandler` (`.../OpNpcHandler.ts:16-20`) both start with `if (player.delayed) { player.write(new UnsetMapFlag()); return false; }`. `delayed` is only cleared at step 1 of the phase-5 turn (E1), which comes after phase 2 (`processClientsIn`), so a packet decoded in phase 2 of tick T+1+n still sees `delayed == true` (`Engine-TS/src/engine/World.ts:619` shows phase 2 also checks `player.delayed`). Consequence (inference): in a chain of `p_delay`s, every phase 2 falls inside a delay, so the chain cannot be interrupted by walk/op clicks at all (see chapter 4). Matches 05 scenario 4 (`tick/scenarios.md` rows T0+1, T0+2).

**E6. What closes a dialogue and clears the weak queue (`closeModal`).** Source: `Engine-TS/src/engine/entity/Player.ts:760-814`
```ts
    closeModal(clearWeakQueue: boolean = true) {
        if (clearWeakQueue) {
            this.weakQueue.clear();
        }
```
- Default argument `true`: **every** plain `closeModal()` empties the weak queue first (`Engine-TS/src/engine/entity/Player.ts:761-763`), before the "nothing open" early return (`Engine-TS/src/engine/entity/Player.ts:768-770`).
- If a modal was open, an `activeScript` in `COUNTDIALOG` or `PAUSEBUTTON` is dropped (`Engine-TS/src/engine/entity/Player.ts:774-778`): a dialogue abandoned by walking away simply never resumes. A script in `RUNNING` state is unaffected (E3: `ScriptRunner.execute` sets `RUNNING` at `Engine-TS/src/engine/script/ScriptRunner.ts:128-130`) - this matters for scripts that call `if_close` on themselves (chapter 5).
- Callers: `clearPendingAction()` (`Engine-TS/src/engine/entity/Player.ts:970-973`), which `stopAction()` calls (`Engine-TS/src/engine/entity/Player.ts:964-967`) and which `Engine-TS/src/network/game/client/handler/MoveClickHandler.ts:30-32` (not for op-clicks) and `Engine-TS/src/network/game/client/handler/OpNpcHandler.ts:47` call in phase 2; the `if_close` command (`Engine-TS/src/engine/script/handlers/PlayerOps.ts:246-248`); `processQueues` when a `STRONG` entry exists or `requestModalClose` was set by the `CLOSE_MODAL` packet (`Engine-TS/src/engine/entity/Player.ts:874-886`, `Engine-TS/src/network/game/client/handler/CloseModalHandler.ts:13`); `p_stopaction` / `p_clearpendingaction` (`Engine-TS/src/engine/script/handlers/PlayerOps.ts:430-437`). 05#10, 05#12.
- Opening a new chat modal also drops a pending dialogue script (`Engine-TS/src/engine/entity/Player.ts:2050-2054`).

**E7. The three player queues and their counters.** `enqueueScript` appends to `queue` (NORMAL/STRONG/LONG), `weakQueue` or `engineQueue` (`Engine-TS/src/engine/entity/Player.ts:841-851`). Normal and weak passes post-decrement the delay on every visit and run an entry when the pre-decrement value is `<= 0` and `canAccess()` (`Engine-TS/src/engine/entity/Player.ts:897-913`, `Engine-TS/src/engine/entity/Player.ts:916-926`). So an entry with delay d runs on visit d+1, a blocked entry keeps counting down and runs on the first accessible visit (05#11-12). `LinkList.all()` caches the *next* node before yielding (`Engine-TS/src/datastruct/LinkList.ts:47-55`, `Engine-TS/src/datastruct/LinkList.ts:67-75`, `Engine-TS/src/datastruct/LinkList.ts:97-111`); a script that appends to the list it is being run from, when the running entry was the last node, does not see its new entry until the next tick (05#13; the engine comment at `Engine-TS/src/engine/entity/Player.ts:892-896` calls this "authentic"). Script commands `weakqueue*`/`queue*`/`longqueue*` forward the delay unchanged (`Engine-TS/src/engine/script/handlers/PlayerOps.ts:135-146`, `Engine-TS/src/engine/script/handlers/PlayerOps.ts:160-170`, `Engine-TS/src/engine/script/handlers/PlayerOps.ts:183-193`).

**E8. Player timers.** A timer is a `Map` entry keyed by script id holding `clock` = tick it was set or last fired (`Engine-TS/src/engine/entity/Player.ts:928-939`). `processTimers` fires when `currentTick >= clock + interval` and (soft, or `canAccess()`), sets `clock = currentTick` *before* running the script, and runs normal timers protected, soft unprotected (`Engine-TS/src/engine/entity/Player.ts:945-961`). There is no catch-up: a blocked timer fires once, late. `settimer` on an existing id replaces the entry and restarts the clock (`Engine-TS/src/engine/script/handlers/PlayerOps.ts:890-900`, `Engine-TS/src/engine/entity/Player.ts:928-939`). 05#16-17.

**E9. Zone triggers are engine-queue entries created in phase 10.** `NetworkPlayer.updateMap()` compares the 64x64 map square and the 8x8 zone with the last ones, and calls `triggerMapzoneExit`/`triggerMapzone`/`triggerZoneExit`/`triggerZone` (`Engine-TS/src/engine/entity/NetworkPlayer.ts:251-283`), which `enqueueScript(..., PlayerQueueType.ENGINE)` (`Engine-TS/src/engine/entity/Player.ts:580-615`). `updateMap` runs in phase 10 (`Engine-TS/src/engine/World.ts:1108`, as in 05#20). The engine queue is processed at step 5 of the *next* tick's phase 5 and each entry needs `canAccess()` (`Engine-TS/src/engine/entity/Player.ts:660-670`). So a teleport in tick T fires the destination's `[mapzone,...]`/`[zone,...]` at the earliest in phase 5 of T+1, and later if the player is delayed or has a chat/main modal open (05#20-21; table row "Steps 6-11 ... or phases 6-11" in 05#22).

**E10. World queue (`world_delay`).** `WORLD_DELAY` only sets `WORLD_SUSPENDED` (`Engine-TS/src/engine/script/handlers/ServerOps.ts:167-170`); `Player.executeScript` then calls `World.enqueueScript(script, script.popInt())` (`Engine-TS/src/engine/entity/Player.ts:2212-2213`), which stores `delay + 1` (`Engine-TS/src/engine/World.ts:1249-1251`). `processWorld` (phase 1) walks the queue, post-decrementing, runs an entry when the pre-decrement value is `<= 0`, unlinks it after `ScriptRunner.execute`, and re-enqueues if it suspends on the world again (`Engine-TS/src/engine/World.ts:534-557`). Computation (inference from 01#4): a `world_delay(d)` called in phase 5 of tick U resumes in phase 1 of tick U+d+2. The script is not any entity's `activeScript` while it waits, so it does not delay, protect or block anybody.

**E11. NPC turn pieces used here.** `Npc.turn()` (`Engine-TS/src/engine/entity/Npc.ts:109-118`): undelay + resume an `NPC_SUSPENDED` script first. `processTimers` (`Engine-TS/src/engine/entity/Npc.ts:550-559`): `ai_timer` fires when `timerInterval > 0 && ++timerClock >= timerInterval`, and the clock resets only after the script ran. `processQueue` (`Engine-TS/src/engine/entity/Npc.ts:561-583`): `npc_queue` delay is decremented only while the NPC is not delayed, runs when `<= 0`. `npc_delay(n)` sets `delayedUntil = tick + 1 + n` and `NPC_SUSPENDED` (`Engine-TS/src/engine/script/handlers/NpcOps.ts:97-101`); `npc_queue(id, arg, delay)` (`Engine-TS/src/engine/script/handlers/NpcOps.ts:159-165`); `npc_settimer(n)` calls `setTimer`, which ignores only `-1` (`Engine-TS/src/engine/script/handlers/NpcOps.ts:293-295`, `Engine-TS/src/engine/entity/Npc.ts:219-223`), so `npc_settimer(0)` turns the timer off; `npc_add(coord, type, duration)` creates a `DESPAWN`-lifecycle NPC, sets it as the script's active NPC and calls `World.addNpc` (`Engine-TS/src/engine/script/handlers/NpcOps.ts:57-67`), which calls `resetEntity(true)` (zeroes all `varn`s) and sets the lifetime (`Engine-TS/src/engine/World.ts:1292-1303`); `npc_del` calls `World.removeNpc(npc, respawnrate)` (`Engine-TS/src/engine/script/handlers/NpcOps.ts:93-95`). 04#4-7, 04#12-13. NPCs run in phase 4, i.e. **before** any player in the same tick (E1); an NPC added by a player script in phase 5 of tick T takes its first turn in tick T+1 (it is added to `World.npcs` at `Engine-TS/src/engine/World.ts:1270-1273`, after phase 4 has passed).

**E12. Teleports and camera.** `p_teleport` -> `PathingEntity.teleport` sets `tele = true`; `jump` only if the level changed (`Engine-TS/src/engine/entity/PathingEntity.ts:287-318`); `p_telejump` additionally sets `moveSpeed = INSTANT` and `jump = true` (`Engine-TS/src/engine/entity/PathingEntity.ts:281-285`). A later `validateDistanceWalked` sets `jump` if the tick's displacement was over 2 tiles (`Engine-TS/src/engine/entity/PathingEntity.ts:323-335`). The `jump`/`tele` bits' effect on the client is in 09-info (not re-read). `cam_moveto`/`cam_lookat` are queued and written in phase 10; `cam_shake`/`cam_reset` are written immediately (`Engine-TS/src/engine/script/handlers/PlayerOps.ts:207-228`, `Engine-TS/src/engine/entity/NetworkPlayer.ts:240-249`; 10#3 and 10#11). Zone changes are detected in phase 10 against the last recorded zone, so only a change of 8x8 zone / 64x64 square triggers anything (E9).
